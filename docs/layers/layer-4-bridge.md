# Layer 4 — Cross-device session and control fabric

Bridge is Pastey's authenticated current-session communication and control fabric across Hosts. It carries ordinary data and bounded control for Agent execution while keeping session delivery separate from task authority. This document owns Bridge membership, peer identity boundaries, ordinary-data routing, and control transport. Legacy code and storage still use **Room** terminology; it refers to the current Bridge session, not a separate product model.

## Current-session peer model

An accepted peer is admitted only by pairing: a one-time 8-digit code, shown on one device and typed on the other, is the password of a SPAKE2 exchange. The exchange binds the Bridge id, both HostRefs, both Ed25519 device keys and both current transport keys, and each side pins the other's HostRef and device key to the Bridge (`bridge_peer_pins`). A code answers a bounded number of guesses, expires, and admits one device. A routeable peer additionally has a current connected endpoint and transport key in `bridge_peers`. Neither accepted nor routeable means a consented or execution-authorized device. The protocol and bounds are in [reference](../reference.md#bridge-authentication-facts).

Bridge is not durable history. The peer table holds the current-session endpoint, liveness, join method, `peer_session_id`, optional logical `HostRef` association, and optional paired-device display reference. The HostRef is learned through an additive join-handshake field and is identity only: it does not make the row routeable, paired, admitted, approved, or capable. Older peers may omit it. Reconnect requires fresh proof of the pinned device key: the requester's query carries a nonce, the peer's offer is signed by its pinned key over that nonce and a single-use nonce of its own, and the requester's `/join` is signed by its pinned key over both nonces and both new transport keys. A changed device key or HostRef is never accepted on reconnect; only pairing with a new code replaces a pin. On reconnect with a changed host, port, or transport public key, Pastey creates a new `peer_session_id`, marks the old route stale, clears its endpoint/key material, and rejects old routes as expired. Old routes do not rebind; the new current session must establish its own HostRef association. Startup recovery preserves an active logical Bridge and its member projection, marks every prior live peer session disconnected, clears runtime endpoint/key material, starts a new local Bridge server, and attempts bounded identity-pinned rediscovery of the same Bridge. A successful rediscovery always creates a fresh exact peer session even if the host and port happen to match the old route. A Bridge without a pin (for example one made before pairing existed) does not try to reconnect and has no routeable peer; its local data stays, and its `pairing_state` is `pairing_required` until it is paired again from its own Bridge details: one device shows a new code, the other enters it there. A code entered under New Bridge never pairs a Bridge this device already has. Pairing a device key other than the Bridge's current pin, including any pairing of an unpinned Bridge, is fresh trust:
- removed: Bridge-scoped runtime authority, Native Agent tasks, Reviews, conversations and retained results, folders shared with the Bridge, and Full Access over it;
- kept: Bridge items and Plans.

Re-pairing the same pinned device key changes nothing. A HostRef is never treated as proof of a physical device; the code is what decides which device is trusted.

Temporary route loss changes liveness/reachability but does not by itself remove current Bridge membership. Explicit leave/Burn is different: before local cleanup removes route keys, the departing Host creates a typed encrypted `bridge_membership.departure` event bound to the exact authenticated current session. The receiver deletes only that peer's current membership/route, revokes Bridge-scoped runtime authority bound to the departed session, and retains its own local Bridge. Paired-device display identity may remain separately. The event is a membership fact, never permission to Burn another Host.

Liveness values are `connected`, `reconnecting`, `disconnected`, `left`, `stale`, and `expired`. Only a connected peer with endpoint/key material is routeable.

The Host probes each exact connected peer on a two-second reconciliation cadence with a bounded (1.8 s) signed liveness request, answered with proof that the peer holds its stored room-server key. Three consecutive failures remove that exact route from selection, change the member to reconnecting, clear Bridge-scoped process authority, and rotate the local server session before recovery; one slow probe across the internet is treated as jitter. A session through the internet carrier is probed with a 5 s bound and ends after four failures ([Connectivity](layer-4-connectivity.md#how-the-internet-path-works)). After bounded failed attempts the truthful product state is disconnected; later retries may still establish a fresh session. A normal Quit signals the lifecycle, discovery, and Bridge servers to stop and relies on this remote liveness boundary. It does not Burn or delete the local logical Bridge.

## Product interaction boundary

**New Bridge** is a non-mutating choice screen. Nearby discovery and refresh only observe available devices. A nearby request is a prompt, not authentication: when the other device's user accepts, that device creates one new Bridge and shows a one-time code, and the requester's user types it to pair; the acceptance itself carries no code, Bridge id, port or key.

**Paired devices.** A code pairing proves the other device's identity key, and both devices remember it as a known device (`known_bridge_devices`). A nearby Join to a known device carries a request signed by this device's identity key, bound to the request id, both HostRefs, a time and a nonce.

When the receiver still knows that key:
- it creates the Bridge pinned to it, without a prompt or code, and shows a notice;
- it answers with a single-use offer signed by its own key, and the requester completes the join with the same identity-proven handshake as a reconnect;
- a Bridge that is not joined within two minutes is burned again.

Anything that does not verify is shown to the receiver's user as an ordinary request. Being Busy (having a Bridge) does not block a known device. Membership grants nothing else: Agent work and terminals still need Review, or the Full Access this device's user gave that device on this Bridge. A Bridge a known device re-creates this way starts without Full Access; it is a new decision for the new Bridge.

Forgetting a known device (Settings → Devices & trust → Paired devices):
- revokes it, and any Full Access it holds here;
- removes every pin to its key;
- ends those Bridges' current sessions, so they need pairing again;
- keeps Bridge history.

A new key paired for the same HostRef supersedes the old one. Burn does not forget a device. Other devices on the network are never trusted by being there. Manual code entry pairs with an existing Bridge's open code, and **Create Bridge** is the only action on that screen that creates an empty Bridge/code. Opening the screen from the sidebar or empty workspace creates no storage record. The Bridge's details panel (opened from its header) shows the pairing state and can show a new code for the open Bridge.

**Devices** inspects the selected Bridge's known members and current liveness. It has no add/find/join action because Pastey does not implement adding another Host to an existing Bridge. Nearby admission belongs to New Bridge.

**Developer Mode** replaces only the selected Bridge's central workspace. The Bridge selection, sidebar, current-Bridge context, member state, and Bridge lifecycle remain in place. A receiver observes authenticated pending terminal requests for its known Bridges without first creating receiver-side Developer Mode UI authority. Accept or Deny is still an explicit Host-local action: that action creates the receiver's short-lived UI session and either consumes the existing terminal admission path once or denies it without starting a PTY.

## Paired-device display identity

Explicit pairing can retain label, fingerprint, pairing method, timestamps, revocation state, and bounded rotation state in `bridge_durable_identities`. This is display/recognition metadata only, separate from the authenticated Bridge pairing pin above. It cannot receive data, auto-join, revive a route, grant consent, or grant capability authority. Full cryptographic paired-key rotation is not implemented.

## Ordinary-data routing

`selected peer` means one explicitly selected current-session accepted peer. `selected peers` means an explicit selected subset. `broadcast to Bridge` means all current routeable peers at resolution time; it is explicit, not a durable group, and later membership changes do not rewrite the operation.

Text supports all three ordinary-data modes and reports per-target outcomes. File, image, and pasted-image actions also support all three; selected-peers and broadcast resolve to target-specific queue children before dispatch. Malformed, duplicate, unknown, mismatched, stale, or unavailable routes fail under the current policy. A selected-peer route fails closed. There is no arbitrary legacy endpoint fallback after validation fails.

## Control transport

Bridge control events are encrypted, typed current-session values separate from ordinary Bridge items. The transport has bounded event/request/response size, expiry, replay cache, per-class rate/burst limits, event-kind allowlisting, and unsafe-field rejection. Replay and rate admission come before anything acts on an event, and a refusal for the rate budget proves nothing was done ([reference](../reference.md#room-control-message-lifecycle-and-backpressure)). The unsafe-field rule covers every envelope and payload field except exactly one capability-owned opaque subtree of specific `native_agent` messages, whose contents Pastey does not interpret; [reference](../reference.md) lists them. Protocol events (capability queries and answers, Native Agent events, Bridge Plan v2) are acted on and not kept; only Bridge Plan v1 events are kept as bounded display history (64 per Bridge, 30 minutes, oldest dropped first), which never refuses anything. Pending decisions (native Reviews, Bridge Plan reviews) keep their own lifecycle in their own stores. The history is a current-session buffer, not durable workflow history.

Bridge Plan control messages remain exact selected-peer only. `selected_peers` and broadcast control routes are rejected. Layer 4 transports a Plan message; it does not authorize it. A delivery receipt says only that transport accepted or exposed an event—not that approval, execution, or a durable relationship exists.

Bridge Plan v1 and v2 coexist explicitly. V1 retains its existing `bridge_plan.*` event kinds and requester/selected-session payload contract. V2 uses only `bridge_plan.v2.review_request` and `bridge_plan.v2.attempt_start`, carries its own exact protocol version and Plan participants, and uses a separate replay namespace. On inbound v2 delivery, Layer 4 resolves the authenticated peer's current `HostSessionBinding`; Core verifies that binding against the reviewed sender/target HostRefs and performs Host admission. Layer 4 does not derive participants, approve the Plan, choose a Host, insert Transfer, or create an execution grant.

Native Agent control (`native_agent.*`) follows the same split. For an inbound invocation or workspace preparation, Layer 4 resolves the authenticated peer's exact current `HostSessionBinding`; Core checks task ownership and performs native executor admission, owned by [Layer 5](layer-5-agent.md); the executing Host's executor Review is required before any capability is prepared or started. A capability's opaque invocation input and terminal output are carried but not interpreted. Bridge membership and an authenticated session never by themselves let a peer run a capability on this Host; only this Host's Review, or the Full Access its user gave exactly that paired device, does.

Room Control delivers correlated current-session completion/control events to the Layer 5 Host coordinator. It does not inspect Plan topology, assume PipelinePrivate is followed by Transform, choose the next primitive, or create semantic step authority.

Developer Mode v0 reuses the same current-session peer resolution, authenticated encrypted Room Control envelope, event expiry, and replay boundary for a distinct `developer_terminal` message family. Terminal frames are delivered directly to the UI-independent terminal service, with separate bounded streaming rate/buffer state; they do not enter the Room Control display history or Bridge item history. Layer 4 transport still does not grant terminal consent: the remote human admission (or the Host's Full Access for that device) and `DeveloperTerminalGrant` are owned above this layer. See [architecture](../architecture.md#managed-workspace-and-developer-mode).

The Bridge detail panel uses one serialized control-inbox pump. Active nonterminal operations refresh automatically; focus/entry refresh and **Check for updates** are fallbacks. Processed or unchanged events do not create duplicate product-state updates or resend delivery.

## Lifecycle boundaries

Disconnect, explicit departure, Burn, and startup recovery invalidate current-session work as applicable; recovery creates no authority. Disconnect retains membership for a possible fresh-session reconnect. Explicit authenticated departure removes the departing peer from current membership but does not delete the survivor's Bridge. Local Burn first cuts local authority off, including Native Agent task/movement authority owned by that Bridge and its pending executor Reviews, then best-effort uses existing authenticated departure/cancellation paths and removes that Host's routes, active server/transfer state, room-control inbox/replay/rate state, candidate/Plan workflow state, Bridge-bound Native Agent envelopes and app-owned retained results, Bridge membership, items, and reusable room material. An authenticated departure applies the same Native Agent authority cutoff for that Bridge on its receiver. Direct local Native Agent tasks without Bridge correlation and user-owned original workspaces are preserved. An unprovable Native Agent apply journal leaves the canonical workspace and uncertain siblings untouched while Bridge authority and its envelope are removed; unknown siblings may remain as orphan disk residue, and burned-room startup still proceeds. Bridge payload items use a per-Bridge wrapping key under the existing installation secret; Burn removes that key before fallible content/database cleanup, so retained Pastey key state cannot decrypt leftover Bridge ciphertext. It preserves user-saved final Inbox files and an independent paired-device display identity only. The durable Burn tombstone is opaque and non-sensitive; it is not product history. Replay, delivery receipts, control inbox entries, logs, and approval records cannot cross a Bridge session as authority. Burn does not prove remote native-process termination across a partition.

## Current limitations

Durable paired-device auto-join, adding a Host to an existing Bridge, generic control-event fan-out, and full cryptographic key rotation are not implemented. Restart recovery is limited to rediscovering the same active logical Bridge's pinned peer device on the LAN, at its remembered address, or through its pinned carrier key; a prior endpoint or navigation is never admission. Burn provides logical deletion and cryptographic erasure through the per-Bridge payload-key lifecycle, but SQLite page/WAL/journal and filesystem block remanence are outside Pastey's physical guarantee. Phase 6.6 coordinates an authored v2 Plan by sending separate exact review/readiness/start/commit events to each current Host route; it does not turn Room Control into broadcast authority. Multi-target fan-out remains limited to ordinary data. Two-device/package validation remains a required manual/release check. On a LAN or overlay, room-server HTTP is still plaintext apart from encrypted payloads and envelopes (through the internet carrier it is inside QUIC), so an on-path observer there sees metadata (Bridge id, transfer ids, sizes, names) and can delay or drop packets. It cannot join, inject, reorder or substitute content, or end a transfer:
- each chunk's encryption binds its transfer, index, total, size and final flag;
- the receiver checks the sender's signed BLAKE3 of the whole file before finalizing;
- unauthenticated chunk requests are refused one at a time and never fail the transfer. The [join audit](layer-4-join-audit.md) records what was found and what remains.

For exact vocabularies and schemas, see [reference.md](../reference.md). For Layer 5 semantic approval and step authority, see [Layer 5](layer-5-agent.md). For validation, see [development.md](../development.md).

## Reaching a peer on another network

LAN discovery broadcasts and cannot cross networks. Two other paths can, and neither changes the session or authorizes anything: an address on a private or overlay network the user runs (Tailscale, WireGuard), and the optional internet carrier (direct P2P through NATs, relay fallback), which carries the unchanged Bridge over a QUIC tunnel to a carrier key pinned through an authenticated session. Both, the Transport–Session contract and the decisions behind them are in [Connectivity](layer-4-connectivity.md).
