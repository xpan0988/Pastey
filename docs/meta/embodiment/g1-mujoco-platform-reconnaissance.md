## Architecture relevance

**SOURCE FACT:** Menagerie's standard G1 scene includes a 29-DOF **position-actuated** model. Unitree MuJoCo's default G1 scene instead includes `g1_29dof.xml` with 29 **motor/torque actuators** and ordered joint-position, joint-velocity, and actuator-force sensors. The Unitree bridge reads those three sensor blocks by array offset and writes torque-like `mjData.ctrl` values. Menagerie `g1.xml` has only four IMU gyro/accelerometer sensors and no ordered motor sensor blocks. Therefore the inspected Unitree bridge cannot be assumed to accept the Menagerie G1 scene without model/control/sensor integration work. This is a substrate fact, not a proposal to perform that work. [Menagerie model](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1.xml#L297-L337), [Unitree scene](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/unitree_robots/g1/scene.xml#L1-L2), [Unitree model](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/unitree_robots/g1/g1_29dof.xml#L382-L510), [C++ bridge](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L165-L180).

**SOURCE FACT:** The simulator is a DDS-facing low-level plant bridge. It does not issue META authority, decide completion, or publish effect acceptance. A future local enforcement point could be located on the controller's command-publication path, provided a single owner of that path is established; this is an **INFERENCE** about a possible insertion point, not a platform enforcement guarantee. The controller retains real-time generation of motor targets. [C++ bridge](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L141-L180), [SDK channel publisher](https://github.com/unitreerobotics/unitree_sdk2/blob/9754cd153af3da471b0fe5f3aa535e426fb11db3/include/unitree/robot/channel/channel_publisher.hpp#L8-L32).

## Menagerie G1 model surface

**SOURCE FACT — variants and control.** `g1.xml` is `g1_29dof_rev_1_0`; `g1_with_hands.xml` adds seven articulated finger joints/position actuators per hand (43 position actuators total); `g1_mjx.xml` is a separate 29-DOF MJX-oriented model. `scene.xml` includes `g1.xml`; `scene_mjx.xml` includes `g1_mjx.xml`. The standard and hands models set `implicitfast`, joint `armature=0.01`, `frictionloss=0.3`, and a `<position>` default with `kp=500`, `dampratio=1`, `inheritrange=1`. The position actuators are named exactly like their joints. No separate explicit `ctrlrange` appears on these actuator declarations; `inheritrange=1` ties control range to the associated joint range. Joint `actuatorfrcrange` is a modeled force bound, not a position control range or physical stop guarantee. [Standard model](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1.xml#L1-L18), [standard actuators](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1.xml#L297-L327), [hands actuators](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1_with_hands.xml#L432-L476), [scenes](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/scene_mjx.xml#L1-L2).

The binding-relevant 29 named hinge joints, mirrored by 29 same-named position actuators, are:

The finger names added to each side are `hand_thumb_{0,1,2}`, `hand_middle_{0,1}`, and `hand_index_{0,1}` (all with `_joint`). Finger ranges differ by side/sign; e.g. left thumb 0 `[-1.0472,1.0472]`, left middle/index 0 `[-1.5708,0]`, right middle/index 0 `[0,1.5708]`. These added fingers are distinct from SDK2's body-motor array and its separate hand messages. [Finger joints](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1_with_hands.xml#L242-L300), [right fingers](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1_with_hands.xml#L359-L417), [Unitree hand indexing](https://github.com/unitreerobotics/unitree_mujoco/blob/main/unitree_robots/g1/g1_joint_index_dds.md#L95-L106).

**SOURCE FACT — observation and contact.** The standard model locates IMU sites at the pelvis (`imu_in_pelvis`, local position `0.04525 0 -0.08339`) and torso (`imu_in_torso`, `-0.03959 -0.00224 0.14792`). Each has gyro and accelerometer sensors with specified cutoff/noise; standard `g1.xml` has no joint-position, joint-velocity, quaternion, contact, or actuator-force sensor definitions. Its free base and joint state remain available to *a direct MuJoCo data observer*, but they are not a Unitree `LowState` path merely because the MJCF exists. Visual meshes disable contact, while collision meshes and four small sphere geoms per foot can participate in MuJoCo contact. The standard scene adds a floor and no explicit `<contact><pair>`. `g1_with_hands.xml` adds finger/palm collision geoms; it keeps the two IMU sensor sets and a `stand` keyframe with hand values. [Standard sites/sensors/keyframe](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1.xml#L61-L67), [torso site](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1.xml#L169-L179), [standard sensors and `stand`](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1.xml#L328-L337), [foot contact geoms](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1.xml#L98-L107), [standard floor](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/scene.xml#L14-L16), [hands keyframe](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1_with_hands.xml#L477-L487).

**SOURCE FACT — MJX difference.** `g1_mjx.xml` uses `timestep=.004`, `iterations=5`, `ls_iterations=8`, disables ordinary geom contacts, models simplified capsule/box collision geoms, and uses lower joint-position gains (base `kp=75`, `kv=2`, with `kp=20`, `kv=2` for ankle/wrist). The `scene_mjx.xml` names explicit contact pairs including feet/floor, self-contact, and upper body/floor, and defines `home` and `knees_bent` keyframes. Its sensor set is richer (local/global velocities, accelerometer, gyro, up vector, orientation) at torso/pelvis. The model changelog records a right-hip-limit correction. The README's hardware-transfer sentence is a **DOCUMENTED CLAIM** about a separate experiment, not physical conformance evidence for META or this bridge. [MJX defaults](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1_mjx.xml#L1-L73), [MJX sensors](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/g1_mjx.xml#L385-L401), [contact pairs/keyframes](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/scene_mjx.xml#L23-L116), [changelog](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/CHANGELOG.md#L4-L18), [README](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/README.md).

## Unitree MuJoCo simulator surface

**SOURCE FACT — connection.** Unitree's default `unitree_robots/g1/scene.xml` includes `g1_29dof.xml`. C++ `config.yaml` defaults to DDS domain `1`, interface `lo`, robot `go2`; selecting G1 and its scene is explicit configuration. The C++ bridge initializes `ChannelFactory` with those settings, chooses the HG/G1 bridge for G1, subscribes to `rt/lowcmd` (`unitree_hg::msg::dds_::LowCmd_`), and publishes `rt/lowstate` (`LowState_`). It also publishes `rt/sportmodestate` (Go2 message type), `rt/wirelesscontroller` if a joystick exists, and G1 `rt/secondary_imu` / `rt/lf/bmsstate`. The G1 `mode_machine` is set to `4` if the scene filename contains `23`, otherwise `5`; this is a source-coded scene heuristic, not proof of hardware type. [G1 scene](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/unitree_robots/g1/scene.xml#L1-L2), [C++ config](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/config.yaml#L1-L14), [C++ launch](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/main.cc#L534-L575), [C++ bridge](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L141-L159), [G1 extras](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L239-L296).

**SOURCE FACT — command semantics.** Each C++ bridge iteration computes, for actuator `i`, `ctrl[i] = tau + kp*(q_target - sensed_q) + kd*(dq_target - sensed_dq)`. Its G1 model's `<motor>` actuators have torque `ctrlrange` values (e.g. shoulder/elbow `[-25,25]`, wrist pitch/yaw `[-5,5]`). The bridge does not inspect `LowCmd.mode`, `mode_pr`, `mode_machine`, `crc`, command age, or a lease when applying the command. The inspected C++ loop reads the *last stored* `lowcmd->msg_` on every iteration. In this path, command loss or a controller process disappearing does not itself zero the command or prove physical stopping. [Bridge command loop](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L161-L180), [G1 actuator limits](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/unitree_robots/g1/g1_29dof.xml#L382-L412), [SDK subscription storage](https://github.com/unitreerobotics/unitree_sdk2/blob/9754cd153af3da471b0fe5f3aa535e426fb11db3/include/unitree/dds_wrapper/common/Subscription.h#L24-L45).

**SOURCE FACT — observations.** The Unitree G1 model defines 29 ordered joint-position sensors, then 29 joint-velocity sensors, then 29 joint-actuator-force sensors, plus pelvis `imu` quaternion/gyro/accelerometer, frame position/velocity, and secondary IMU sensors. The C++ bridge copies the three motor sensor blocks into `LowState.motor_state[i].q/dq/tau_est`; it copies primary IMU values when named sensors exist, computes RPY from quaternion, emits `LowState.tick = round(mjData.time / 1e-3)`, publishes frame position/velocity through `SportModeState`, and publishes the secondary IMU separately. `tau_est` is the simulated joint actuator-force sensor value, not measured hardware torque. No contact list, complete base orientation/pose object, applied `ctrl`, or command target is published as an explicit G1 completion witness by this bridge. [G1 sensors](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/unitree_robots/g1/g1_29dof.xml#L413-L510), [C++ state mapping](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L175-L223), [G1 secondary IMU](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L258-L290).

**SOURCE FACT — timing/lifecycle.** C++ runs the bridge via a `RecurrentThread` configured with `1000` microseconds; physics is a separate MuJoCo loop driven by the model timestep and viewer speed/synchronization, with pause and reset paths. The source provides no hard wall-clock scheduling guarantee or atomic sample/command correlation. On startup the bridge waits for `mjData`, initializes DDS, then runs; its thread function sleeps forever and has no modeled command-loss shutdown transition. When the physics UI exits, allocated model/data are deleted and the process exits. Thus simulator `tick`, callback arrival time, and host monotonic time have distinct meanings. [C++ bridge period](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L156-L160), [physics stepping/pause](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/main.cc#L386-L494), [startup/exit](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/main.cc#L500-L575).

**SOURCE FACT — Python path differs.** `simulate_python/config.py` defaults to 5 ms simulation timestep and 20 ms viewer period; `unitree_mujoco.py` sets `mj_model.opt.timestep` and sleeps only the residual step time. The Python bridge uses the HG `LowCmd_/LowState_` for `ROBOT=="g1"`, subscribes to `rt/lowcmd`, computes the same PD-plus-feedforward `ctrl` **on message arrival**, and publishes low/high state on recurring threads at `model.opt.timestep`. It does not set G1 `mode_machine` or `tick`, publish G1 secondary IMU/BMS, or compute IMU RPY in the inspected bridge. Python `ChannelPublisher.Write()` returns whether the DDS write completed (and optionally waits for a matched reader); that result is not motor actuation or effect acceptance. The Python callback's last written `mjData.ctrl` persists unless changed by another writer/step path. [Python config](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate_python/config.py#L1-L12), [Python launcher](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate_python/unitree_mujoco.py#L20-L82), [Python bridge](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate_python/unitree_sdk2py_bridge.py#L14-L153), [Python write result](https://github.com/unitreerobotics/unitree_sdk2_python/blob/65691c8a8bc53b98d3976dba4dbf9d5d20b2e7f5/unitree_sdk2py/core/channel.py#L111-L145).

**OPEN QUESTION:** The repository's `g1_23dof.xml` scene contains placeholder/dummy joints yet declares a 29-entry motor list, while its DDS index document gives a distinct 23-DOF motor mapping. The C++ bridge loops over `m->nu`; therefore a 23-DOF binding should not infer physical motor correspondence from scene name or array length alone. The 29-DOF default scene is the source-clearest case for this reconnaissance. [23-DOF model](https://github.com/unitreerobotics/unitree_mujoco/blob/main/unitree_robots/g1/g1_23dof.xml#L417-L482), [23/29 DDS mapping](https://github.com/unitreerobotics/unitree_mujoco/blob/main/unitree_robots/g1/g1_joint_index_dds.md#L5-L62), [C++ mode heuristic](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L243-L250).

## SDK2 command and state surface

**SOURCE FACT — low-level messages.** G1/HG `LowCmd_` has `mode_pr`, `mode_machine`, 35 `MotorCmd_` entries, reserve fields, and CRC. A `MotorCmd_` contains `mode`, `q`, `dq`, `tau`, `kp`, `kd`, and reserve. The SDK's G1 low-level examples set mode `1` for enabled and `0` for disabled, publish `q`/`dq` targets, feedforward `tau`, and gains. In the simulator bridge those fields implement the explicit PD-plus-feedforward formula; the bridge does *not* implement hardware mode handling. The 35 wire slots are a fixed message capacity, not 35 active G1 body motors in the 29-DOF scene. [C++ LowCmd](https://github.com/unitreerobotics/unitree_sdk2/blob/9754cd153af3da471b0fe5f3aa535e426fb11db3/include/unitree/idl/hg/LowCmd_.hpp#L21-L59), [MotorCmd](https://github.com/unitreerobotics/unitree_sdk2/blob/9754cd153af3da471b0fe5f3aa535e426fb11db3/include/unitree/idl/hg/MotorCmd_.hpp#L18-L63), [C++ example](https://github.com/unitreerobotics/unitree_sdk2/blob/9754cd153af3da471b0fe5f3aa535e426fb11db3/example/g1/low_level/g1_dual_arm_example.cpp#L264-L281), [Python example](https://github.com/unitreerobotics/unitree_sdk2_python/blob/65691c8a8bc53b98d3976dba4dbf9d5d20b2e7f5/example/g1/low_level/g1_low_level_example.py#L122-L135).

**SOURCE FACT — low-level state.** G1/HG `LowState_` has two `version` integers, `mode_pr`, `mode_machine`, `tick`, 35 `MotorState_` entries, `imu_state`, wireless remote data, reserve, and CRC. Each `MotorState_` offers `mode`, `q`, `dq`, `ddq`, `tau_est`, temperature, voltage, sensor values, and a motor-state word. The **message definition** offers these fields, but the **simulator** fills only `q`, `dq`, and `tau_est` per motor, plus IMU/tick/mode-machine fields described above; unpopulated fields must not be treated as observed temperature, calibrated voltage, firmware, or motor health. The 29-DOF DDS mapping puts right shoulder pitch/roll/yaw at indices `22/23/24`, elbow at `25`, and wrist roll/pitch/yaw at `26/27/28`; `mode_pr` selects pitch/roll versus A/B interpretation for ankle/waist fields. [LowState](https://github.com/unitreerobotics/unitree_sdk2/blob/9754cd153af3da471b0fe5f3aa535e426fb11db3/include/unitree/idl/hg/LowState_.hpp#L23-L88), [MotorState](https://github.com/unitreerobotics/unitree_sdk2/blob/9754cd153af3da471b0fe5f3aa535e426fb11db3/include/unitree/idl/hg/MotorState_.hpp#L19-L84), [index map](https://github.com/unitreerobotics/unitree_mujoco/blob/main/unitree_robots/g1/g1_joint_index_dds.md#L31-L62), [bridge field assignment](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L175-L209).

**SOURCE FACT — publication/subscription and transport.** Low-level clients initialize a CycloneDDS channel factory with a DDS domain and network interface; publisher and subscriber are separately initialized on topic/type. The C++ example uses `rt/lowcmd` and `rt/lowstate`, CRC-checks incoming state, copies `mode_machine` from state, and runs command writer/control threads at 2 ms. The Python example uses the same topics/types, state callback, CRC on outgoing command, `MotionSwitcherClient` mode release, and a 2 ms recurring publisher. These are *example timing choices*, not guaranteed rates. C++ `SubscriptionBase` provides a local 1000 ms default `isTimeout()` observation and `wait_for_connection()`; neither automatically stops the simulator plant. The G1 C++ `LowCmd` publisher offers `check_mode_machine()` and regards returned mode `0` as simulation, but this helper is not an authority check. Python `Write(timeout)` concerns DDS writer/subscriber matching and write return, not a control watchdog. ## Missing physical semantics

## G1/MuJoCo validation boundary

MuJoCo can exercise the integration semantics of exact binding, publication gating, local timing assumptions, modeled state freshness, three completion strata, partial/unknown outcomes, simulated command loss, restart, contact, and recovery when corresponding observers and fault injections exist. The inspected public stack alone does not implement those META semantics or an independent oracle. Simulator time and a 1 ms/2 ms/5 ms configured loop do not prove hardware wall-clock bounds. A DDS write or RPC return is disposition evidence only; an effect claim requires observed state and a qualified witness. Neither simulated joint tracking nor the Menagerie README's separate transfer claim validates physical G1 safety, real stopping distance, calibration, wear, environment uncertainty, or autonomy. [Bridge timing/control](https://github.com/unitreerobotics/unitree_mujoco/blob/1eb6642e3f3fdfb7fb13a9794fd6a2dd93ea0e7d/simulate/src/unitree_sdk2_bridge.h#L156-L209), [SDK example period](https://github.com/unitreerobotics/unitree_sdk2/blob/9754cd153af3da471b0fe5f3aa535e426fb11db3/example/g1/low_level/g1_dual_arm_example.cpp#L159-L200), [Menagerie README](https://github.com/google-deepmind/mujoco_menagerie/blob/main/unitree_g1/README.md).

## Open questions

1. Which *single* scene and control path will Phase 0 name: Unitree's 29-DOF torque scene, a direct Menagerie position-control path, or a later verified integration? Their current observation and enforcement surfaces differ.
2. Who owns the sole `rt/lowcmd` writer when a native controller and local enforcer coexist, and how are competing DDS publishers excluded or detected? No priority/arbitration guarantee was found.
3. What command-loss behavior and protective transition can be demonstrated in the chosen simulator path, including pause, process death, network loss, and restart? The inspected bridge retains prior command/control values.
4. Which direct MuJoCo observations, if any, will be available to an independent effect witness for contact, applied control, base state, and time? SDK2 `LowState` alone omits some of these.
5. For a 23-DOF G1 scene, how should its dummy XML joints/actuators and documented 23-motor DDS indices be reconciled before binding? This does not block a 29-DOF-only reconnaissance decision.
6. What real-device identity, calibration, firmware, response bounds, and conformance evidence exist outside these public simulation sources? This cannot be answered by a MuJoCo run.
